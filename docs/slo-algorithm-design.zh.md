状态：设计与迁移记录，2026-09-24。A0 独立枚举器、A1 统一转移及 A2 共同计划构造已落源码；后续 Metal 小样本已取得真实完整见证提交，仍未完成正式并发与稳定容量验收。A3–A5 仍在实施。
承接原 RFC v2、[完整实施与验收清单](slo-implementation-plan.zh.md)及交接中的执行/资源基础。
原始设计审查基点为 `88dc391b` 加当时工作树；后续实测冻结版本另列，不能仅用提交号重现全部代码。
第三方源码只阅读，未引入依赖或复制实现。本文的算法组合是 Ferrum 的待验证设计，不声称学术首创。

## 1. 我们要解决的问题

目标是在固定模型质量、设备、资源和请求集合下，最大化满足 TTFT、TPOT、客户端可见文本 ITL 的持续服务容量。
主验收的既定工程硬门为：successful output tokens/s 分别达到 llama.cpp 与同构建 Ferrum Off 的至少 95%，六项延迟各比 llama.cpp 降低至少 10%。
这些是执行方已预声明的量化默认；统计不确定性另列，用户另行指定时以用户要求为准。
Metal 与 CUDA 各自验收 Qwen3.5-9B 的 C4/C8/C16/C32。请求完整完成，历史失约保留，不能通过丢弃长请求提高成绩。

这决定了三个边界：

1. 同一请求的提前输出不能抵消随后任意长的可见停顿。
2. 调度器消耗的 CPU 时间、维护、输出准备和真实 kernel 路线都属于成本。增加搜索若使设备等待，可能直接损害目标。
3. 达标容量是实测结果；有限时域计划、成本模型的拟合优度和编译通过都不是替代品。

用户提出的容量表达式正是核心研究问题。更完整地，固定配置 `theta`（模型质量、硬件与资源）和到达/长度分布族 `W_lambda`，定义：

```text
C*(W, theta) = sup over pi in CompleteRequestsPolicies of sup {
    lambda :
    P_lambda,pi(TTFT <= T1) >= p1,
    P_lambda,pi(TPOT <= T2) >= p2,
    P_lambda,pi(ITL  <= T3) >= p3,
    SuccessRate_lambda,pi >= p4,
    queue is stable
}
```

`lambda` 是请求到达率，`pi` 是遵守资源/输出合同、只使用当时可得信息的调度策略。
到达过程的突发性和请求分布需要固定，不能仅凭相同平均到达率认为工作负载相同。
使用 `sup` 避免假定最大值必定能取得；实现寻找更好的策略，未证明达到所有策略中的全局最优。
理论中的队列稳定不能由有限测试证明，工程验收用预声明持续窗口、队列/最老等待趋势及排空记录检验。

概率口径也属于问题定义：TTFT/TPOT 按请求统计，主表 ITL 按非空 SSE 可见文本间隔统计；失败、缺失和未完成不能当作零延迟。
报告同时保留全体 offered 请求的成功/错误/拒绝分母与延迟样本资格。
三项边际达标不等于同一请求联合达标；若声明联合目标，应另用请求级最大可见间隔构造联合事件，并保留 N/A 与 Unknown。
只有同一请求总体上的三个事件，才能用联合概率关系推导；不能把 pooled ITL 事件分布与请求分布直接相交。

输出吞吐 `G_pi(lambda)` 是实际成功输出 token 数除以观察时间，不等于 `lambda`。
在正式相同负载点仍需满足 `G_pi >= 0.95 * G_llama` 且 `G_pi >= 0.95 * G_off`，并满足六项相对延迟门槛。
这些是产品验收约束，不通过修改 `C*` 的请求样本或输出长度来满足。
局部规划分数只是寻找策略的工具，不作为 `C*` 或实际 `G` 的替代指标。

QoServe 论文的 artifact DOI 指向名为 Niyama 的归档及 `niyama_asplos2026` 官方分支，这是同一阅读链，不能误列为两套独立验证。
参见 [QoServe 论文与 artifact appendix](https://www.microsoft.com/en-us/research/wp-content/uploads/2025/10/QoServe_CC_final_v2.pdf)、[归档](https://zenodo.org/records/18218177)。

一个直接影响取舍的差异：QoServe 的交互 deadline 使用入口时间、TTFT 预算和 token 序号计算累计期限；JITServe 也研究累计 deadline 下的 goodput。
这种目标与逐次可见文本 gap 不等价。例如首个可见输出在 10ms，第二个在 120ms；若累计期限分别是 100ms、120ms，两次均满足，但可见 gap 是 110ms，不能满足 20ms ITL。
这是指标的数学反例，不是对其论文实验结果的否定。

JITServe 论文 §5（p833）的实现允许等待超限丢弃，Appendix C（p842–843）的理论模型允许抢占请求永不完成；两者不是同一个实现断言。
Theorem 4.1 / Appendix E 的竞争界限于其模型，不继承为我们的 CompleteRequests 或可见 ITL 保证。
参见 [正式论文](https://www.usenix.org/system/files/nsdi26-zhang-wei.pdf)。
同理，QoServe 将部分工作降级等待空闲的策略不直接满足我们对所有已接受请求的进展要求。

**最终选择：一个共享执行状态机、一个有界规划器、一个独立提交校验器。**
简单可检查的共同计划是起点，剩余预算用于改善计划；成本覆盖不足时进入明确的完成优先策略。
不把论文机制拼成多个独立调度器，也不为每个模型另写一套队列。

| 我们选择什么 | 放弃的方案 | 接受的代价 |
| --- | --- | --- |
| 可检查的共同序列 + 有界改善 | 每轮穷举所有未来 token；只检查本轮的贪心排序 | 可能漏掉可行解，必须保留 Unknown 并度量漏解损失 |
| 真实路线与状态约束下动态填充 | 用固定 token 数代替时间；无条件选择最大 chunk | 校准和状态表达更复杂，需要限制动作域与控制开销 |
| TPOT 与相邻间隔同时约束 | 仅依赖累计 token deadline | 可用于大批处理的余量更少，必须靠执行效率和合理填充补偿 |
| 完成优先并保留服务欠账 | 仅让迟到请求等待空闲；丢弃困难请求提高 goodput | 过载时可能牺牲更多健康请求的延迟，必须公开全体结果 |
| 后端共享策略，成本与能力分域 | Metal/CUDA 分裂为两套策略；共用未经验证的性能常数 | 保留统一语义，同时承担两套校准与实机验收成本 |

## 3. 驱动重设计的历史证据

重设计前的 Metal C8 小样本诊断完成 8/8 请求、1608 输出 token、0 错误，但当时完整可行见证提交为 0。
786 个已提交波次中，732 个以计算预算不足进入完成优先路径。
这是对原 8 个请求的诊断，不是正式并发验收，也不是“786 个请求失败”。

代码审查显示：节点已有模拟状态，但扩展又模拟历史前缀；物理路线解析还另行重放前缀；同一候选的 shape 在选择和推进时重复解析。
逻辑候选按配置最大宽度枚举，未先收窄到当前 ready 集合。
因此问题是状态转移边界没有统一，不能仅以增加缓存或提高 2ms 预算解决。

成本覆盖也是独立问题：同轮 heldout 的 1574 个查询有 59 个 Unknown，1515 个 Known 中有 36 次低估；终态和部分 prefill 路线缺样本。
即使规划变快，也不能将这些路线假定为已知。
系统 CPU sample 的业务符号被 release stripping 去除，尚无精确函数耗时归因；上面重复计算的结论来自源码，不是 profile 百分比。

原始证据位于仓库外 `slo-goal-20260922/workspace-startup-first8-{enforce,calibration}-r1` 及 calibration audit。
小样本数据只用于提出和否定设计假设；不写进产品胜出表。

## 4. 状态、动作和三类承诺

沿用现有请求 owner，规划只读一个带版本的快照。快照包含：

- 请求 incarnation / work generation、已完成逻辑范围、KV/recurrent 状态和 readiness；
- 原始 ingress、first/last commit、已提交 token 数、不可抹去的失约记录、prefill 净进度及服务欠账；
- 输出 credit、已知的服务端可见输出状态、维护义务与资源 epoch；
- 固定版本的成本模型、合法路线目录、模型/数值策略/设备指纹。

动作是一段真实可返回调度器的工作：`Decode`、`PrefillChunk`、原生 `Mixed`、有界 `Maintenance/Restore`。
普通 decode 每请求每波最多一个目标 token。split 的 decode 和 prefill 是两个动作。
缩小实际工作必须返回真实回执，不能在 fallback 中执行更多 token。

| 承诺 | 可建立的依据 | 不代表什么 |
| --- | --- | --- |
| 物理和语义合法 | 真实资源 authority、identity、范围、输出 credit、提交 fence | 不代表按时完成 |
| 当前模型下的有限共同计划 | 固定快照上的合法序列、成本范围和全部义务检查 | 不代表未来未知到达下整请求达标 |
| 客户端 SLO 达标 | 固定条件下实际客户端六项延迟、完成率、吞吐和队列证据 | 不能由前两者直接推出 |

成本 `T_plus` 是经校准的规划值；它超过期限只能说明当前模型下不能认证该计划按时，不能证明真实执行或所有合法计划都不可能。
`ProvenImpossibleUnderModel` 必须另有可靠下界或硬边界，不能使用样本最小值、保守上界、beam 裁剪或搜索超时冒充证明。

## 5. 统一状态转移，消除重复推演

转移语义如下；实际接口为 scheduler 的 `PlanningExecutionContext`、`PlanningExecutionState::project` 和 `simulation::advance`：

```rust,ignore
transition(parent, logical_action, frozen_context, budget)
    -> Result<TransitionDomain, UnknownReason>;

// 每个物理分支分别包含：
// resolved_action + canonical_cost_shape + predicted_interval
// resource/output delta + next logical state + obligation result
```

当前 A1 实现由引擎捕获同一 epoch 的请求、资源和路线，搜索节点同时持有逻辑状态与不可变执行后继。
`simulation::advance` 只投影新增动作；完整逻辑、时间和输出检查成功后才保留联合后继。
生产适配器不再逐节点从根重放路线；旧 resolver API 通过显式兼容适配器重放，不作为生产性能路径。
最终选中序列仍从同一捕获的根状态、以新的实际时间独立重验，随后由原提交 guard 检查当前真实状态。
这两个边界不同：重新模拟不等于重新捕获 live authority，任何规划后继都不携带执行许可。

A1 的硬件无关状态、预算、独立小模型及当前集成工作树检查已通过；真实 Metal 小模型也已验证
partial→final 后继、重新捕获后的 decode/mixed 与完整 native/host 记录一致，且纯投影不提交工作。
冷 mixed 的物理池不足保持 Unknown；测试经真实容量维护和执行后才验证驻留路线，未把冷状态重标为已准备。
上述检查只验证转移和执行语义；后续 9B 集成诊断的提交证据见文末，不能据此推断正式客户端 SLO 达标。

一次 transition 同时完成语义检查、合法物理路线解析、资源/输出投影、时间推进和义务检查。
搜索节点持有该转移产生的轻量不可变状态；扩展一个节点只计算新动作，不从初始状态重新计算整条路径。
规划状态不持有可提交 permit，不分配真实 KV，不修改 lifecycle。父子共享不变数据，分支差异显式保存。

路线如果依赖尚未知的终态、位置或维护结果，必须保留声明的全部相关分支，或返回 Unknown。
同一个逻辑动作必须对父状态域中每个可达分支成立；后继域包含全部后继，整波规划成本取分支最大值，有效期限取最小值，资源与义务逐支检查。
“每个分支各自存在不同的后续动作”不等于存在一条共同序列。第一阶段只接受共同动作序列，不按尚未观测到的 token 内容选择分支。
以后如支持条件策略，其分支只能基于执行后真实可观测的回执，需另行定义检查器。
分支上限是资源保护措施，不能通过只保留最快路线获得可行结论。
只有完整未来相关状态等价的分支才可合并；canonical cost shape 相同或 hash 相同不构成资源/路线状态等价证明。
资源、成本、逻辑进度使用同一个转移结果，避免三份模拟各自接受互相不兼容的状态。

提交校验独立从真实快照重放**选中的一条计划及其必需路线分支**，不信任搜索缓存。
随后只给第一波申请真实权限，并重验时间、generation、资源、输出 credit 与执行路线。
因此复用的是规划中重复的数据流，物理提交边界仍有独立检查。

复用键至少覆盖 snapshot/cost/route/resource/output epoch 与父状态身份。
跨 wave 的旧计划只能作为构造顺序的提示；到达、取消、EOS、容量变化或成本漂移后不能直接作为新证据。

## 6. 先构造共同计划，再有界改善

### 6.1 义务

内部 token-commit 域沿用 RFC：首 token 期限 `ingress + F`；已生成 `n >= 1` 时下一期限为：

```text
min(last_commit + I, first_commit + n * P)
```

两项分别保护相邻间隔和累计速度。内部前缀 TPOT 约束比最终 TPOT 更严格，这是明确接受并需要消融的保守性。
prefill 使用净参考工作与固定起点的进度里程碑，restore/recompute 不重复赚取进度。
里程碑是防止推迟工作的控制约束，其失败不直接等于 TTFT 已不可能。

未选请求与 blocked 请求仍在义务集合中；blocked 的资源唤醒时间未知时不能假设下一波自动 ready。
过去的失约记录永久保留，但不因此放弃该请求仍可保护的未来义务：TTFT 已晚的 decoder，后续 ITL 仍可受保护。
只对已不可逆过期的具体义务采用 CompletionOnly 处理；里程碑、首字和下一 token 分别判断。
在事务开始固定每项义务的 Protected/CompletionOnly 范围，不能在搜索耗时后把新超时义务临时移出 Protected 来通过检查。

### 6.2 候选由当前合法前沿生成

每次快照只建立一次身份索引与稳定轮转 tie-break。节点推进后重新计算相关紧迫性、prefill 欠账、readiness 和到期服务顺序，再从实际 ready 数、后端合法 batch 桶、prefill 对齐和成本覆盖中取有限候选。
final prefill 产生的新 decoder、已服务 decoder 的下一期限都会改变排序；不能固定使用根节点的优先级。
至少尝试当前可用的完整 decode cohort、必要紧急前缀、服务欠账到期者，以及能够推进临近首字义务的 chunk。
Mixed 仅在后端支持、共同成本受覆盖时进入。

对允许合法中间进度的 piecewise reference，chunk 候选保留后端最小对齐、参考 granule、当前最大值和合法尾块，
并在既有数量预算内补充 `alignment × 2^k` 阶梯。例如对齐为 1、granule 为 32、上限为 128 时，
16 和 64 也能进入搜索。附加预算先覆盖较大的中间档位；这是有界搜索启发式，不假设耗时随 chunk 单调。
V1 精确端点参考不做这种扩展，所有新候选仍须具有已知的真实波次成本，并通过资源与最终执行校验。
中间档可以同时避免大块长占用和小块重复开销；针对性测试验证这种共同可行性，但不替代实机成本覆盖或服务 SLO 验收。

不穷举请求幂集；也不假定 batch/chunk 越小一定更快。候选裁剪记录原因，裁剪失败返回 Unknown。
同一请求集合内，可以根据相同后继状态下的时间/资源支配关系剔除更差动作。
跨不同后继状态不能只因 tokens/s 较低就删除动作：它可能推进了另一个紧急请求。

### 6.3 构造性起点

按以下顺序尝试少量完整序列：

1. 重用上一轮计划的顺序提示，以真实回执后的状态重新验证；
2. 按紧迫性安排共同 decode 服务，在剩余时间内放入合法 prefill；
3. 对临近首字期限或欠账到期的工作，尝试一次有限次序调整。

每条序列必须同时考虑选中和未选请求、后续 decode、prefill 里程碑及必要维护。
“每个请求单独下一轮能来得及”不构成共同计划。
简单策略可能找不到计划；有 incumbent 不是算法的无条件前提，也不是保底承诺。

### 6.4 有界改善

有共同可行计划后，再尝试扩大合法 chunk、合并可用 decode、调整少量动作次序，或增加有限 beam 分支。
保留原始小候选策略作为消融基线；复杂度只有改善真实容量才保留。

通过相同义务与相同验证范围后，使用 RFC 的净输出/净 prefill 进度代理分数比较计划。
所有评分都包括规划和执行占用；不同 horizon 的裸 tokens/s 不直接比较。
比较时读取同一个实际时间作为排名基点，将从原事务开始已耗的规划时间只计一次，不按候选边重复累加。
节点中的模拟时间是相对执行进度，不能代替实际 CPU 时钟；最终校验始终从最新实际时间重新计算期限。
排序分数只是提议顺序，不因分数已计算便跳过这次时间校验。
prefill 信用只用于排序，不进入外部 successful output tokens/s。
`beta/gamma` 仍是待实验参数，不新增一组未经验证的“智能”权重。

可选优化不得挤占最终校验预算。到达软截止，返回仍能通过最终校验的 incumbent；没有则明确 Unknown。
若 incumbent 失效，不以“之前检查过”为由执行。

```text
capture：固定全部义务、模型版本、资源与输出状态，启动同一计算时间窗
seed：在有限次尝试内，用 transition 构造并检查共同计划
improve：只在剩余搜索预算允许时扩展/替换，保留已验证的 incumbent
check：从实际当前时间独立重放选中计划，包含必要尾序列和全部路线分支
publish：只给第一波申请真实权限，并再次检查时间与执行身份
observe：只用真实回执更新逻辑进度、成本和服务欠账
```

任一阶段无法完成时走明确的 Unknown/恢复分支。恢复重新申请真实权限，其提交单独计数，不能标作 SLO 共同计划。

### 6.5 计算预算

设 `N` 为参与义务的请求数、`E` 为实际允许的状态转移总数（包括路线分支）、`H` 为被选计划长度、`C_transition` 为一次投影成本。
目标结构为根索引/排序 `O(N log N)` 加 `O(E * (C_transition + C_generate))`，最终检查另计 `O(H * C_transition)` 及必需分支。
`C_generate` 包括节点优先级和候选维护，直接重排时含 `O(N log N)`；若采用增量索引，应单独验证其更新与失效规则。
若一次投影为 `O(N + R)`，`R` 是相关资源条目数；不得把路线解析和复制成本隐藏为常数。

同时限制 wall time、转移次数、候选数、路线分支数和内存。每个慢接口必须可预算检查；只在外层循环计时不能提供硬执行时间上界。
当前 2ms 是待验证的产品配置，不是理论常数。先降低结构性重复成本，再用实测决定时间份额。
以规划 P50/P99、最终检查 P99、设备空闲、超预算次数和最终吞吐量化开销；release 保留可用符号用于归因。

## 7. 有限范围与长期风险分别处理

共同见证显式给出 `validated_through`、Protected 集合、CompletionOnly 集合、模型版本和终端剩余义务。
验证范围按真实时间和到期义务定义；`lookahead_waves` 只是计算上限，不能把波数少误认为未来负担小。

在事务开始固定搜索边界、有限尾序列的终点和义务生成规则。尾序列使用同一 transition，检查到终点为止所有到期义务与规定的近期共同服务。
新首 token 产生的后续 decode 义务仍按规则纳入；不能仅检查入口时已经存在的义务。
尾序列全部计入同一转移数、计划长度、分支数与墙钟预算，不在每推进一波后再次延长终点，不另开隐含搜索预算。
若缺少所需成本或尾序列无法在预算内完成，返回 Unknown；不放行一个只检查了首波的“完整计划”。
尾序列结束仍有更远未来，所以这种验证仍是有限范围。

要宣称递归可行，必须另证明一个终端集合在合法后续策略下保持可行，且成本扰动、未来准入、KV 增长和输出条件满足假设。
当前不具备这份证明。第一阶段采用“有限见证 + 每波重新验证 + 慢速风险反馈”，明确不宣传整请求硬保证。
后续是否引入可验证的周期服务模板，应由测量和小状态反例决定，不为追求形式完整把每个请求模拟到 max_tokens。

慢路径跟踪请求到达、剩余 prefill、活跃 decode 的服务负担、队列趋势、成本覆盖和低估。
输出长度预测可以用于容量风险估计，但不作物理许可或提前终止依据；长度超出统计范围触发重新评估。
新活跃请求必须与现有义务共同评估，不能只看首字是否能完成。
在 CompleteRequests 模式中，这控制执行时机和时间承诺，不改变已接受请求的完成责任。

## 8. 成本模型是算法的一部分

选择“物理路线分域 + 简单预测器 + 独立残差校准”，而不是用高维精确键无限扩张样本表。
数值策略、设备、provider、冷/热路径、维护及终态语义必须隔离；同域内可对 batch、KV 长度、prefill offset/count 建立经 heldout 检验的分段模型。
范围内插值也必须被验证；未知路线或范围外查询仍为 Unknown。

规划值表示为 `T_hat + residual_quantile + drift_margin`，记录边界、样本来源、有效期和覆盖。
覆盖从整个波次的真实结束点建立，不把各算子 P99 相加称作整个波次 P99。
训练、校准、heldout 分离；低估频率、幅度及与失约的关联共同报告，不能只看 R²。
自适应选批改变分布时需要重新检验；经验残差分位数不是无条件概率保证。

校准采样根据合法动作图和预测失败分布制定，覆盖会被执行的边界、terminal、维护和 batch/KV 组合。
这比盲目重复同一短请求有意义。不能为了消除 Unknown 降低样本门槛、改写 TTL 或套用另一个 binary 的 profile。
成本不足时继续合法完成请求并采集实际路线；不为收样本在生产中执行额外推理工作。

## 9. 进展、输出和算子三项不可让步的约束

### 完成请求

恢复路径沿用真实服务机会欠账：只有实际提交同伴工作、该请求当时可服务却被略过才增加欠账；只有真实进度回执才清零。
欠账到期者按欠账、原入口和稳定轮转排序，最老且可服务者成为首波必需工作；其他人的欠账继续保留。
不能要求所有到期者必须同时装入一个物理上不可能的 batch，也不允许无限被“下轮再服务”的预测取代。
若无法同时满足其他请求的 SLO，必须报告冲突并进入恢复策略，不能隐藏牺牲者。

进展论证依赖有限活跃集合、每次合法工作有进展、资源/输出最终恢复及执行最终返回。
慢消费者永不恢复或无限超容量到达时，不能承诺所有请求在有限时间内完成。
硬接收容量/取消/明确超时仍按现有产品合同处理，主比较不启用因 SLO 风险拒绝请求。

### 客户端可见输出

token commit 不保证产生非空可见文本；UTF-8、reasoning、stop、工具协议和网络合并都会影响事件。
因此内部 deadline 证明只针对明确的 token-commit 边界。服务端可见输出年龄与输出队列状态用于风险反馈，不能冒充客户端最后收包时间。
只有在映射及输出延迟条件另行成立时才能推导外部边界；主验收始终直接测非空 SSE 文本事件间隔，保留合并造成的停顿。
客户端不可控传输延迟的影响单列，不能通过丢弃这类样本“修复” ITL。

### 算子效率

如果当前合法执行路线本身过慢，调度不会凭空减少执行时间。Metal/CUDA 各自优化实测关键路径。
算子、混合编排、调度策略和输出隔离分别做消融，再组合验收。
普通波次成本下降可能使更大的 batch/chunk 进入可行集合，这是 kernel 与调度的直接协同；必须用相同质量和真实整波数据验证。

## 10. 可证明什么，如何反驳自己

| 命题/假设 | 验证方法 | 结论边界 |
| --- | --- | --- |
| transition 不修改权威状态，且逻辑进度与物理路线一致 | Rust 状态测试、不同分支隔离、取消/partial/维护回执测试 | 语义与资源正确性 |
| 找到的共同序列在给定成本模型下满足声明范围 | 小状态精确枚举 oracle 对照独立检查器 | 不证明启发式总能找到，也不证明真实成本服从模型 |
| 单 token 内部期限足以约束同边界 ITL/前缀 TPOT | 虚拟时钟公式、边界与溢出测试 | 不直接推广可见 SSE |
| 完成优先策略不因持续选择短请求饿死长请求 | 有界活跃集、持续短任务插入、欠账/真实回执测试与条件论证 | blocked 永不恢复等情况不适用 |
| 规划开销有界且新结构更有效 | Rust planner benchmark、带符号 CPU profile、真实 workload | 配置预算不是操作系统 WCET 保证 |
| 成本覆盖和安全余量足够 | 分域 heldout、漂移注入、低估与 SLO 关联 | 经验有效性，需要持续复核 |
| 吞吐和六项延迟同时达标 | 双后端固定基线、交错重复、原始客户端证据 | 仅对实测模型/配置/负载成立 |

必须包含的反例：两个请求各自独占能赶上但共同不能；持续推迟 prefill；低成本第一波后必须维护；终态改变路线；小 batch 更慢；
提前输出后长 gap；已有失约不能重置；未知 EOS；只剩一个请求的收尾；输出 credit 竞争；成本低估；最终校验期间取消；模型版本切换。
精确 oracle 使用独立的小模型枚举，不调用生产 beam 作为“正确答案”。复杂度统计服务于性能定位，不用固定调用次数替代行为测试。

[吞吐最优排队模型](https://arxiv.org/html/2504.07347v1)提供保留连续混合批处理的理论动机，但其到达、批次成本和内存假设不能直接覆盖 Ferrum。
队列稳定也不推出 P99 达标；本文不宣称通过采用 work-conserving 策略就获得其吞吐最优定理。
