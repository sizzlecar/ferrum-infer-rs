# RTX 5090 上的驻留容量与 Q8 投影布局

**保留主干默认。** `4c2b58108` 修复了 27B GGUF 在 8、16 并发下的主要吞吐回退。相同二进制在 C96 下，显式 32 驻留的两轮分别为 590/621 tok/s，默认 Auto 80 仅为 205/182 tok/s，首 token P99 从 8–9 秒增至 30–37 秒。扩大容量会挤占热执行目录所需的资源。九种权重的 ShareGPT 验收也未满足吞吐与三项尾延迟均不退化的条件。

在上一轮冻结的 ShareGPT 测量中，27B GGUF 候选在 C8 和 C16 的吞吐分别比主干低 4.28% 和 3.21%。两档实际在途请求都少于旧上限 32。本轮调查扩大驻留上限为什么会影响低并发，并验证修复后的默认入口。[上一轮实测](performance-auto-serving-capacity-rtx5090.zh.md)

## 启动时发生了什么

主干 `0603698cf` 在 32 个驻留请求下选用了 `predecoded-f32`。候选 `5d72c31c5` 先用压缩布局搜索到 81 个名额，再尝试在相同的 81 个名额下预解码。可用预算为 29,186,378,183 字节，压缩布局的浅 decode 峰值为 29,153,538,496 字节，预解码布局为 29,247,910,336 字节。后者超出预算 61,532,153 字节，启动日志记录了回退到 `compressed` 的原因。

这份 Q4_K_M 权重含有 Q8 投影。48 个层各有一对 5120 × 48 的 A/B 投影，96 份 F32 系数共 94,371,840 字节，与两版实际静态分配的差额一致。CUDA 实现可以将符合条件的相邻预解码投影一起提交。旧报告中的两版各执行 24,452 个 decode 波次，平均波次耗时从 19.35 增至 20.35 ms。915 个 prefill 波次的均值分别为 90.14 和 90.08 ms。这里记录的是宿主观察到的波次时长，逐算子 GPU 时间没有采集。[预解码布局](../crates/ferrum-kernels/src/backend/cuda/vnext_ops/transformer/q8act_attention/upstream/q8_predecode.rs) · [CUDA 执行](../crates/ferrum-kernels/src/backend/cuda/vnext_ops/transformer/q8act_attention/upstream.rs)

## 修复

`4c2b58108` 先在原有容量下验证权重布局、捕获预热峰值与驱动显存余量，再用选中的布局编译和拟合更多驻留请求。对两个版本均可容纳的旧负载，扩大并发上限不再优先消耗预解码所需的显存。扩容发生额外编译时，初始化前再核一次驱动余量。[布局选择](../crates/ferrum-engine/src/product_composition.rs) · [容量搜索](../crates/ferrum-engine/src/product_composition/serving_capacity.rs)

驻留数表示可以同时保留生成状态的请求数。达到上限后，调度器把新接受的请求放进等待队列。已有请求结束或取消、释放相应资源后，调度器再从队列准入。等候时间计入首 token 延迟。较长的请求可能更早占满缓存。等待队列也有独立上限，满时调度器拒绝新请求。每个 decode 波次能推进的请求数由单步批宽另行约束。[调度器](../crates/ferrum-scheduler/src/implementations/continuous.rs) · [等待队列配置](../crates/ferrum-types/src/config.rs)

## 复测方法

在同一张 RTX 5090 上顺序运行两个对照。第一组使用相同的 `5d72c31c5` 二进制、`--max-num-seqs 32` 和相同的 27B GGUF，分别指定 `--q8-projection-weight-preparation predecoded-f32` 和 `compressed`。从服务日志核对实际生效的布局。第二组以正常的 `ferrum serve` Auto 参数启动修复版和主干，核对两个程序各自选择的容量、布局和实测性能。

正式客户端沿用 v0.20.1 的 Rust `bench-serve`。两种 27B 使用同一份冻结 ShareGPT 样本，每档 C8/C16 都测两轮，每轮 200 个正式请求和 8 个预热。4B 至 35B 的其他 Qwen 每轮 64 个正式请求和 10 个预热。GPT-OSS 每次起服务时测 32 个正式请求和 2 个预热，两次分别起服务，自然 EOS。精度、输入输出筛选、参数、原始门限和命令与第一轮验收一致。吞吐按服务返回的成功输出 token 总数除以计时时长总和计算。合并两轮的 P99 从逐请求和相邻可见 SSE 事件重新计算，逐轮门限另行判断。额外的 C96 排队试验使用短输入，单列统计。[各模型的原始条件与复现命令](performance-auto-serving-capacity-rtx5090.zh.md)

## 固定 32 个名额，只更换权重布局

| 客户端并发 | 实际 Q8 布局 | 成功请求 | 输出 tok/s | 首 token P99（ms） | 每输出 token P99（ms） | 可见 SSE 间隔 P99（ms） |
|---:|---|---:|---:|---:|---:|---:|
| 8 | 预解码 | 400/400 | 346.90 | 692.46 | 27.19 | 119.65 |
| 8 | 压缩 | 400/400 | 329.76 | 705.75 | 28.35 | 120.71 |
| 16 | 预解码 | 400/400 | 515.69 | 1360.18 | 48.45 | 160.11 |
| 16 | 压缩 | 400/400 | 500.56 | 1044.36 | 38.31 | 161.49 |

压缩布局相对预解码的 C8、C16 吞吐分别低 4.94% 和 2.93%，同一档的两轮方向相同。两种布局逐条输入长度、输出 usage 均相同。预解码额外使用了 90 MiB 静态显存。两臂观测到的 SM 时钟 P10/P50/P90 都是 2850/2865/2895 MHz，温度中位数均为 63°C，预解码和压缩的功耗中位数分别为 504 和 488 W。硬件采样含时间间隙。固定名额后仍重现吞吐损失，支持把上轮主要吞吐退化归因于 Q8 布局回退。C16 的首 token 和每输出 token P99 在这次对照中反而是压缩布局较低，尾延迟需独立验收。

本次固定 32 的预解码进程在 C16 第一批有 5 条请求的首 token 时长约 1360 ms，之前的主干只有 2 条落在相近区间。两轮 400 条数据的 P99 对这几条请求很敏感。客户端记录可定位到第一个批次，缺少每条请求在服务端的排队和执行分解，无法把该差异归到某个 CUDA 算子。

相同 32 个名额下，两臂仍各执行 24,452 个 decode 波次，平均波次耗时为预解码 19.30 ms、压缩 20.41 ms。宿主等待完成的往返时间为 15.13 和 16.29 ms，提交时间为 4.14 和 4.08 ms。相同观测口径下，prefill 波次均值分别为 88.70 和 89.07 ms。

## 96 个请求同时到达时

修复版 27B GGUF 默认可同时保留 80 条请求状态，每轮最多解码 32 条。在同一服务上，以 C96 发送短输入，实际输入 76–79 token，每条生成 64 token。预热 2 条后计时 192 条，客户端维持最多 96 条在途。169 次健康采样中有 115 次看到排队。队列最深时有 64 条等待。在另一张快照上，47 条已进入 prefill 阶段，32 条处于 decode 阶段，17 条仍在排队，合计 96。观察到的驻留峰值为 79。快照按请求所处阶段计数，处于该阶段的请求还需争用单轮执行名额。

192 条均成功，零拒绝、零错误，计时 60.29 秒，输出 12,288 个 usage token，203.80 tok/s。压测前后均为零活跃、零排队。首个可见 token 的 P50 为 20.56 秒、P99 为 31.02 秒，这包含排队和处理输入所花的时间。每输出 token 的 P99 为 211.78 ms，可见输出间隔 P99 为 1284.90 ms。该负载能完成请求，超过交互延迟门限。这一轮独立于正式 ShareGPT，只有一次计时。

复现 C96 时使用同一个发行版客户端，`TOKENIZER` 指向 27B 实际 tokenizer。服务器沿用正式计时的 `comparison` 模型别名、2048 上下文和 2048 单步 token 预算。

```sh
ferrum bench-serve --base-url http://127.0.0.1:28441 --model comparison \
  --tokenizer "$TOKENIZER" --target-backend cuda --dataset random \
  --random-input-len 64 --random-output-len 64 --ignore-eos \
  --temperature 0 --sampling-seed 42 --seed 42 --enable-thinking false \
  --concurrency 96 --num-prompts 192 --warmup-requests 2 --n-repeats 1 \
  --latency-slo ttft:2000,tpot:50,itl:100 --fail-on-error --max-error-rate 0 \
  --timeout 600 --out bench.json
```

在主干完成相同 ShareGPT 计时后，也向同一进程发起相同 C96 负载。主干同时最多驻留 32 条，轮到其余请求时才从队列取出。两边 192 条的输入和输出长度逐项相同。主干用 19.38 秒完成，吞吐 634.09 tok/s，首 token P50/P99 为 7.42/7.84 秒，每输出 token P99 为 49.20 ms，可见 SSE 间隔 P99 为 293.10 ms。把驻留上限从 32 增至 80 的修复版吞吐低了 67.86%，首 token P99 约为主干的四倍。

服务端压力试验开始时，两边各有 34 个可重用的执行程序。主干结束时仍有 34 个，修复版触发了执行目录代次切换，结束时仅剩 1 个。修复版的 backing 资源延后了 296 次，主干为 0。两者完成相同的 12,222 次 decode 操作，分别用了 447 和 448 个 decode 波次。修复版有 147 个波次走驻留 decode 快路径，主干有 421 个。修复版在宿主编码和提交 decode 上耗时 26.80 秒，主干为 2.31 秒。服务端数据可以定位到热执行目录丢失和昂贵的重新提交。单个请求的首 token 时间无法拆出等待哪一项资源花了多久。

在修复版上，按序列保留的两个固定状态池分别增长 6,492,782,592 和 138,608,640 字节，KV 池缩小了 536,870,912 字节。受管显存观测高点为 29,186,184,864 字节，与 29,186,378,183 字节预算只差 193,319 字节。主干的九个池在同一负载前后保持原大小。资源维护会尝试回收空闲执行槽位，为保证捕获中的地址安全，可以同时清除可回收的执行目录。[受阻分配的维护](../crates/ferrum-runtime/src/resource/plan_runtime.rs) · [执行槽位回收](../crates/ferrum-runtime/src/resource/dynamic_pool_set.rs) · [执行目录失效](../crates/ferrum-runtime/src/completion.rs)

当前调度先给等待请求分配序列状态，然后才决定本轮能执行哪些请求。因此，已经进入 prefill 阶段的请求可以持有约 147 MiB 的这两类固定状态，却仍在等 GPU 执行名额。下一项架构改动应让同一轮调度先选出能继续执行的已有请求，再按剩余的批宽、token 数和 prefill 分块预算准入新请求。因慢客户端而暂时停住的请求可以保留其状态，它空出的执行位置仍能服务其他请求。这需要在异步准入前后复用一次选批决策，并验证暂停、恢复、取消和所有请求都受阻时的前向进展。现有布局修复只调整启动规划。[异步准入](../crates/ferrum-engine/src/continuous_engine/inner/token_admission.rs) · [连续选批](../crates/ferrum-scheduler/src/implementations/continuous.rs)
