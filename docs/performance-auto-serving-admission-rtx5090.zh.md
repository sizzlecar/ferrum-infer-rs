# RTX 5090 文本服务的请求准入实测

11 月 22 日在同一张 RTX 5090 上重放此前使 27B GGUF 吞吐降至约三分之一的 96 并发负载，并用 4B 的短输入和混合输入检查扩大容量的收益。主干为 `0603698cf`，此前出现过载回归的版本为 `4c2b58108`，本文分别列出 `aa30a65a5` 及后续候选的测量。[目标与完成条件](goal-auto-serving-capacity.zh.md) · [此前的布局和资源回收证据](performance-auto-serving-layout-rtx5090.zh.md)

## 请求在什么地方等待

27B GGUF 过去能给最多 80 条请求保留状态，每一轮最多推进 32 条解码。实测中提前为最多 79 条分配状态，把受管分配推到离预算不足 200 KiB，34 个热执行程序只剩 1 个。同一版显式限制 32 时保留了全部 34 个。等待执行的请求既占显存，又使正在生成的请求变慢。[上次的同一二进制对照](performance-auto-serving-layout-rtx5090.zh.md)

本轮候选根据编译模型的物理成本，判断能否在执行当前一批时准备下一批。用最终权重布局、实际页增长和预备的工作区估算，两批各 32 条、每条 2048 token 的 4B Q4_K_M 需要 11.12 GB，27B GGUF 需要 35.66 GB，受管预算为 29.19 GB。程序只在空间足够且有输入要跨多个预填充分块时提前准备。遇到压力，先选本轮能继续执行的已有请求，再用剩余的执行位和 token 预算准入新请求。已经接收、尚未分配状态的请求进入等待队列。一条活跃请求结束、取消或暂时停在输出端时，调度器会重新判断能否推进等待者。[物理成本](../crates/ferrum-execution/src/driver/composition.rs) · [等待和选批](../crates/ferrum-scheduler/src/implementations/continuous.rs) · [执行端准入](../crates/ferrum-engine/src/continuous_engine/inner/token_admission.rs)

- README 测量沿用冻结的 ShareGPT，文件 SHA-256 为 `35f0e213ce091ed9b9af2a1f0755e9d39f9ccec34ab281cd4ca60d70f6479ba4`，种子 42。服务保留对应历史权重、上下文和批 token 设置，驻留上限由各版 Auto 自行选择。4B 至 35B 的六组 Qwen 在每档并发各测 64 请求 × 2，两种 27B 各测 200 × 2，GPT-OSS 用两个独立进程各测 32 请求并保留自然 EOS。逐模型筛选、tokenizer、模板、参数和旧参照见[原始条件](performance-auto-serving-capacity-rtx5090.zh.md)。

- 吞吐等于成功请求的服务端 usage 输出 token 之和除以计时时长之和。首 token 延迟从发请求到首个可见文本。每输出 token 延迟取首末可见时间差除以 `usage_output_tokens − 1`。可见输出间隔取相邻 SSE 文本事件的时间差。每轮独立判定历史门限。合并 P99 使用逐请求或逐事件的原始样本，保留轮次供复核。[Rust 客户端计量](../crates/ferrum-bench-core/src/client_slo.rs)

## 普通启动时的长上下文

从 4B 服务命令去掉上下文、批 token、显存利用率、KV 类型和缓存覆盖项，使用默认的 262,144 上下文。两批各 32 条请求全到这个长度时，编译计划给出 556.95 GB 峰值。版本 `aa30a65a5` 因此只预备 32 条。在这个配置下的混合 C48，主干和该版各完成 288/288 请求，成功输出吞吐为 335.70 → 532.88 tok/s，三项 P99 分别为 7,963.01 → 5,551.68、146.52 → 117.75、236.66 → 187.33 ms。两侧最多都驻留 32 条。主干的热执行程序从 34 个降至 0，该版仍保留 34 个。

`793c9d772` 在相同的编译计划上求出可容纳两批请求的最大单请求长度。4B 普通启动结果为 10,480 token、29,170,321,712 字节，预算为 29,186,378,183 字节。引擎检查已发布的所有请求，使用实际分词后的输入长度及请求自己的最大输出长度。只有这些请求全部落在上界以内时才使用额外准备容量。CPU 实际编译计划的回归测试还重新计算了所选长度与再加一个 token 各自的峰值。[长度核算](../crates/ferrum-execution/src/driver/composition.rs) · [请求生命周期](../crates/ferrum-engine/src/continuous_engine/sequence_registry.rs)

该版在普通启动的第一组配对中最多驻留 48 条。混合 C48 的两侧各完成 288/288 请求，主干 → 该版吞吐为 335.53 → 489.61 tok/s，首 token P99 为 7,764.32 → 8,377.41 ms，每输出 token P99 为 136.48 → 128.39 ms，可见间隔 P99 为 255.22 → 205.30 ms。候选首轮有 16 条请求首 token 超过 7 秒，此轮主干有 2 条。该版新增 16 次 backing 准备延后，保留了 34 个热执行程序。正式计时前均已完成标准 C8/C16 和短输入 C48。这个结果同时给出了额外容量的收益和首 token 尾延迟的代价。

交换主干和候选的启动顺序后，混合 C48 吞吐为 363.27 → 467.71 tok/s，首 token P99 为 7,666.65 → 8,996.64 ms。随后运行相同普通启动参数的 `aa30a65a5`，只预备一批时得到 564.90 tok/s，三项 P99 为 5,743.07 / 84.10 / 186.19 ms。这比整批提前准备的同窗结果更快，三项尾延迟也更低。两种策略首轮面对相同的 16,693 个输入 token。完整原始记录显示，整批准备版在第 5 次采样时将受管显存从 6.12 GB 提到 7.77 GB，当时采样到 32 条活跃、16 条仍在排队。

`867c97602` 用下一轮能处理的预填充分块数和队列中确实需要多块的请求数共同限制额外驻留。默认一轮预算 2,048 token、通常每块 512 token，最多支持为 4 条多块请求提前准备。短输入仍按原有批宽处理。若实际输入、最大输出和受管预算无法支持这部分准备，队列继续等待真正空出的执行位置。

## 序列状态池越过执行批宽时的分配

`867c97602` 在普通启动的 4B 混合 C48 最多驻留 36 条。三轮各版均完成 288/288 个请求。主干、同一候选显式 32、候选 Auto 顺序的吞吐分别为 358.61、533.44、485.33 输出 tok/s。首 token P99 为 7,665.60、6,801.85、9,550.03 ms。每输出 token P99 为 116.45、124.38、145.91 ms。可见间隔 P99 为 229.19、200.55、210.39 ms。Auto 算术和流协议检查均通过。C16 冻结样本的吞吐分别为 1,336.04、1,329.08、1,324.04 tok/s。这组低并发数据含两个正式轮次，作为继续反序核验的依据。

从 32 条继续准备时，显存中 FP32 固定序列状态池从 1,610,612,736 字节增至 3,221,225,472，FP16 固定状态池从 37,748,736 增至 75,497,472。最多 36 条和最多 48 条两种策略都多预留了同样的 1,648,361,472 字节。单条固定状态只占 51,511,296 字节。池在存在一次实际短缺时，会按已驻留总量申请可选余量，直至碰到池或设备上限才重试精确用量。短缺次数减少仍会触发相同的首次分配。零碎的新请求会租用已经分配的空闲显存，观测应同时看分配量、使用量和用户延迟。[池的维护和回退](../crates/ferrum-runtime/src/resource/dynamic_pool_set.rs)

`f1f7ed703` 让 Auto 的固定状态及临时工作区按单轮实际执行批宽摊销可选显存，现有捕获工作区与检查点继续按编译计划计入。超过该余量的实际申请仍可按需增长。用 token 或页数计价的长驻 KV 池继续按自身增长策略处理。每个物理池在健康接口报告 `optional_growth_ceiling_bytes`，便于把显存规划、实际分配与用户体验对应起来。[物理池及请求核验](../crates/ferrum-runtime/src/resource/dynamic_pool_tests.rs)

## 默认长上下文的 CUDA 解码

普通 4B 混合负载的独立调度跟踪中，第 33 条请求等待准入的时间从 7.19 秒降至 0.19 秒。仍有四条稍晚到来的请求超过 7 秒才看到首个 token。一条 504 token 输入在抵达后约 3.03 秒获得准入，3.28 秒完成前 256 token，至 12.17 秒才推进最后 248 token。在其中 8.73 秒的间隔里，跟踪记录了准入和下一轮开始，缺少能够将整段时间归给特定函数或设备操作的事件。

## 已观察到的低并发尾延迟差异
