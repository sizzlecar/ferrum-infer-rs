# 发布回归决策方案

2026-09-06。本文确定回归范围、成本和放行规则，并给出实施顺序。
当前已有基础 CI、主分支必需检查和 Rust 模型回归 runner。范围选择器现已提供全量 diff 分析、代表选择、缺口和已声明费用估算，并接入代码 PR 的 CI 报告；自托管 Metal/CUDA 的必需数值检查已接入 CI，当前只覆盖 RMSNorm 的已列形状；现已把模型 runner 已实现的行为接成按 profile 合并的任务，并增加实际报告与预先任务的校验。它只覆盖 ModelRuntime，其他检查器绑定、小合成架构、费用历史、长尾调度和完整发布证据校验仍待完成，计划或模型任务通过都不能放行发布。
具体运行步骤见 [Release regression](release-regression.md)、[真实 GPU 数值检查](backend-numerics.md) 和 [候选版本与安装包准备](release-candidate-automation.md)。候选准备工具已统一工作区版本、内部依赖及锁文件更新，staging 接收目标版本；它们尚未接通自动租卡回归与正式发布。

## 最终原则

先确定本次必须验证的行为，再在满足这些要求的方案中降低费用和等待时间。
不能用通过比例、模型数量、时间已耗尽或 HTTP 200 替代正确性断言。
每次发布都从“上次正式版本 → 当前候选”的全部改动计算范围，包含多个 PR 之间的相互作用。

## 四层验证与执行频率

| 层次 | 验证内容 | 何时执行 |
| --- | --- | --- |
| 模型声明和协议 | 小型配置、文件依赖、模板、tokenizer 边界、stop、schema、tools、历史缺陷；不下载全部权重 | 每个代码 PR 的确定性测试；文档 PR 按现有 CI 仅检查内容和链接，修改产品承诺会增加下次发布要求 |
| 实际后端与小合成架构 | 对受影响算子、精度、布局、形状、状态边界做参考数值比较；小模型检查完整执行连接 | PR 验证受影响后端；发布验证宣传硬件目标的最小实际运行及联合改动；编译不算实际运行 |
| 真实模型和最终安装包 | README 全部快速开始路径；性能快照按实际架构抽样；追加本次受影响量化、协议和状态组合 | PR 按改动范围验证；发版用最终资产完成必需路径，不在此时才首次调查已知缺陷 |
| 长尾与长期场景 | 其他支持组合、长上下文、持续运行和低频交互 | 定时按预算轮转，优先新增、从未实测、历史失败和最久未测组合；影响本次发布承诺的已知失败必须解决 |

“支持 3 种 GPU、100 个模型”不默认意味着每次跑 300 个完整模型，也不意味着少量样本证明全部 300 组合。
登记每个宣传组合的支持状态、真实执行路径、代表关系和依据。不能仅靠模型品牌分组；attention、recurrent、MoE、量化解码、模板和布局不同可能增加必测项。
README 快速开始必须按宣传的模型、后端、默认容量和命令运行。性能快照按架构抽样，不机械地全量复测每个型号。

## 从改动生成必测项

每项记录行为、适用入口、后端/精度、输入边界、检查器、预先确定的容差、证据位置，以及 passed / failed / not_run / inconclusive 状态。
共享推理改动覆盖 run 和 serve；只影响某一入口时说明另一入口不受影响的依据。

| 改动 | 必须检查的行为 |
| --- | --- |
| 下载、缓存、安装 | 空缓存、必需文件齐全、版本一致性、失败重试、已有缓存、实际安装启动 |
| tokenizer、模板、parser、API | marker、历史、reasoning、同步/SSE、工具与终止语义 |
| sampler、grammar、stop | logits 到实际 token 选择、约束启动与结束、用户 stop/EOS、截断后的解析 |
| scheduler、KV、batching | 相关架构的分段/连续执行、并发、取消后复用、真实容量边界 |
| kernel、量化、架构、工具链依赖 | 对应硬件/精度/布局/形状的参考数值比较、真实模型；性能路径改变时同机比较 |
| 未映射的生产改动 | 扩大所属组件范围并补充映射，不能自动视为无需回归 |

## 当前计划器如何落实范围

[CLI 范围分析](../crates/ferrum-bench-core/examples/regression_plan/scope.rs)读取 base 和 candidate 的 Git 对象，使用完整 diff（重命名包含旧、新路径），不按最后一个 PR 或当前工作区内容替代发布区间。
`--stage release` 要求 `--base` 指向候选可达的正式 `vMAJOR.MINOR.PATCH` 标签中 semver 最高的版本；指向候选自身的标签不作为前一版本。这里依据仓库标签约定，不调用 GitHub Release API 验证是否公开发布；运行前必须取得完整的相关历史和标签。PR 与 nightly 不使用这项正式标签基线校验。

[纯版本识别](../crates/ferrum-bench-core/src/release_regression/version_change.rs)比较两端的根 manifest、成员 manifest 和锁文件。只有后态完整符合候选准备器生成的协调版本更新，才把这些已证明的 Cargo 路径收窄为 `Build`，保留构建、安装及发布基线要求。额外依赖、features、构建参数、成员变化或其他文本差异都会保留原来的保守分类；不支持的成员通配符、排除项、缺失输入也不能收窄。同一区间中的 engine、模板、kernel 等改动仍累积加入计划，不会被最后的版本更新抹掉。只接收路径的库接口没有这个内容证明能力，仍保守处理 Cargo 改动。

[路径映射](../crates/ferrum-bench-core/src/release_regression/impact.rs)也区分已经核实的调用关系：`bench-core` 的请求关联头、JSONL journal、profile 和 trace 被生产代码使用，产生 `Observability` 契约与每个后端的有限真模型抽样义务；不会仅因观测改动推断全部算子数值或精度矩阵需要重跑。已核实的版本/回归工具和 CLI 模型回归模块只归验证范围；未知模块仍扩大范围并报告缺口，不把所有 tests/examples 都当作验证专用。

[代表选择](../crates/ferrum-bench-core/src/release_regression/selection.rs)使用实际 `execution_path`：架构抽样按架构、协议和执行路径分组，协议义务还保留后端区别。不同执行路径不能互相代替；共享计算等改动仍按精确目标组合展开。每项需要模型的共享义务只分配给一个代表。若初选集合没有完整检查器绑定，会先从可用且 scope 匹配的配置中补入有完整绑定的代表，再唯一指派；没有可用绑定仍报告缺口。不会因多个模型都兼容而重复分配；每条 Quick Start 则绑定自己的 profile，各自必测，不能由别的配置补位。

CLI 输出当前为 `schema_version: 2`，记录 `release_base_tag` 和 `version_refinement` 的结果、路径或回退原因；架构/协议 scope 也包含 `execution_path`。目录仍为 `checks: []`，表示目录没有额外声明绑定；CLI 会加入现有模型 runner 的内置能力，并输出 `model_tasks`。能力声明不能写成已执行或通过，未实现的行为和其他证据层仍保留缺口。计划生成本身不执行租卡、模型回归或正式发布。

### 已接入的小型模型任务门禁

[model_gate](../crates/ferrum-bench-core/examples/model_gate.rs) 的 `prepare` 从计划的实际指派生成每个 profile 的预期任务，绑定 staging 二进制、版本、模型、后端与检查配置；不支持的模型义务会在租卡前报错。它不负责启动机器或 runner。执行时给现有 runner 传入 `--expected-task` 和相符参数，Rust 的答案、stop、JSON、工具及 SSE 断言产生逐项结果，再由 `verify` 校验完整任务集合。缺失、重复、失败、未结束或配置不符的报告都不能通过，不能用测试数或 PASS 文本补齐。

Quick Start 使用正常 README alias、自动选择后端和 `--disable-thinking`，保留默认容量和模板，使用受控提示词与输出预算。子进程省略显式 `--backend` 并去掉继承的 `FERRUM_*` 配置，只记录去除的键名；PATH、CUDA 可见设备及 HF 缓存/认证等仍保留。run-ready 与 serve-health 必须给出相符的实际后端，run 还须记录正确的请求模型；serve 的状态必须为 healthy，HTTP 200 不能替代就绪。绑定本地模型任务须预先记录规范绝对路径，执行器在加载前规范实际路径并比较；普通 public alias 保留原选择器。配置或二进制版本不符会在加载前失败。Quick Start 复用同一 profile 的 basic 检查，不新增模型加载；HTTP 检查共用一个 server，run 的 basic 与 stop 基线/回放仍保留原有独立进程。

当前绑定包括加载、基本推理/自然结束、Quick Start、历史回放、用户 stop、结构合法性及工具结果续接的已实现入口；工具选择/交接、reasoning alias、长度、scheduler/KV、性能等未实现义务仍不能补位。门禁消费 runner 实际断言链产生的报告，不独立重放原始响应，也不是任意手写报告的真实性证明。architecture/precision/execution_path 仍是任务声明，后端观测不能替代各项数值或路径证明。

输出只声明 `model_runtime`，保留其他计划缺口且固定 `release_approved: false`。安装、help/doctor、首次下载、数值、CI 和正式发布前的完整证据门禁仍需单独完成；自动租卡、全计划执行与发布闭环尚未接通。

## 可执行的量化标准

| 项目 | 放行或处理标准 |
| --- | --- |
| 必需行为 | 未满足项为 0；失败、未执行、不确定和缺证据都不能抵消 |
| 影响范围 | 未解释的生产改动为 0；代表配置须说明覆盖路径及遗漏范围 |
| 历史缺陷 | 适用的历史回归不得失败；可在 CPU 复现的问题优先留下确定性反例，验证旧实现失败、新实现通过 |
| 协议 | 按精确语义断言，如 stop 不泄漏、schema 合法、tool 名称和参数一致、取消后资源可用 |
| 数值 | 按算子、精度和形状预先校准参考误差界限，并用已知错误验证检查器；没有有效参考或容差就记录缺口 |
| 性能 | 按同硬件、模型、精度、输入输出长度和并发比较；在看候选结果前登记允许退化界限、测量方法和不确定性判据 |
| 资源 | 不超过宣传或配置的真实内存/容量边界；不能通过悄悄降低默认上下文或并发让快速开始通过 |
| 时间目标 | 常规热缓存 PR CI 25 分钟内；候选和输入准备后的常规验收/晋升 45 分钟内；这是初始改进目标，超时不等于可以少测 |

数值容差和性能退化界限不是所有模型通用的单一百分比。它们必须作为检查器的显式配置登记，而不是运行后凭观感判定。
性能区间跨过事先登记的界限时为不确定；继续测量须遵守成本预算，预算用尽仍不能记为通过。
发布报告同时保留完整端到端时间和各阶段时间；冷构建、下载、排队、新后端验证不能从用户总等待时间中消失。

## 成本、选样与避免重复

费用估算 = 各设备预计计费时长 × 对应实时单价 + 存储与传输费用。
分别登记构建、排队、下载、模型加载、用例执行、导出和释放资源的时间。并行设备分钟用于费用，实际关键路径用于等待时间。
历史样本不足时给观测值和估算区间，不声称已有可靠 p95。

执行流程按以下规则建设；当前实现计划、估算与有限模型任务校验，不承诺全局最优调度、自动租卡或自动缓存调度：

1. 固定 README、联合改动和适用历史缺陷的必测项。
2. 当前先固定 Quick Start，再优先选择覆盖更多剩余义务的代表；同等覆盖按已登记总耗时、同币种费用和稳定 ID 排序。分配义务前优先补齐可用的完整检查器绑定，再在匹配代表中按绑定和估算排序；缓存是否可用仍需执行准备时核实。
3. 同一模型加载后连续执行相关检查，下载和构建尽量在启动付费 GPU 前完成；必须在 GPU 上准备的部分计入账单。
4. 生成选择与省略理由、预计费用、时间和资源上限。执行中达到费用上限时暂停新增开销并保留未完成状态，调整资源或延期；只能削减非必需长尾工作。
5. 完成后导出证据并释放资源，记录重复下载、重建、重试及 GPU 空闲费用。

每项既有证据关联输入、检查器、执行依赖、模型与模板、构建选项、硬件配置。无法证明仍适用则重跑。
第一版仅允许显式核实的独立检查复用，不自动推导全仓依赖图。
最终资产的快速开始和安装验证必须完成；上传重试使用同一份已验收资产，不重新构建。
checksum 用于识别资产，不能证明行为正确。

## 完整例子：修复 GPU A 的 INT4 量化错误

以下数量、耗时和价格纯属演示，不是 Ferrum 当前支持矩阵、实测成本或固定发布配额。

假设产品支持 GPU A/B/C 和 100 个模型，已登记 8 类架构执行路径；本次修改 GPU A 的 INT4 kernel，影响其中两类。
假设选出的 8 个架构代表配置已经包含 README 的 3 个必测配置，以及 GPU A 上受影响的两个真实模型。

### 1. PR 阶段先复现和修复

- 用小型张量构造实际错误，检查符号、尾块、布局和相关形状边界；旧实现必须暴露数值差异。
- 修复后跑对应 Rust 单元/契约测试、工作区和相关后端检查。
- 在 GPU A 上跑受影响的真实算子差分和两个模型的必要 run/serve 行为。测试同一实际错误路径，不能只有返回非空的冒烟结果。
- 确认修改隔离在 A 的实现后，B/C 不因为这个 PR 重跑 100 个模型；共享路径若也改变则扩大范围。
- 若多个修复涉及同一解码路径，一起稳定代码，再执行联合验证。检查通过后 PR 合并。

### 2. 发版前一次性生成联合计划

从上次正式版本收集所有已合并改动。若还有模板、stop 或 KV 修改，把这些行为加入同一份计划。
如果新增行为没有被上述 8 个代表覆盖，追加配置；不能坚持“最多 8 个”。

本例的候选计划是：

| 内容 | 本例选择 | 选择原因 |
| --- | --- | --- |
| 轻量模型声明与协议 | 100 个模型的小型 fixture | 成本低，尽量早发现文件、模板和能力声明问题 |
| 后端运行 | A/B/C 各自最小实际运行；A 增加 INT4 边界差分 | 验证每个宣传硬件，深入本次受影响的算子 |
| 真实模型 | 8 个代表配置，已包含 3 个 README 配置及 A 的两个受影响配置 | 覆盖架构抽样、产品承诺和本次改动，共享加载避免重复 |
| 其他支持组合 | 放入定时轮转，并披露本次未测范围 | 不能据此宣称其他全部模型/GPU 组合已经真实回归 |

### 3. 先估算，再运行

纯演示：8 个配置每个运行 3 分钟，共 24 GPU 分钟；设备准备和小型算子验证合计 6 GPU 分钟，总共 30 GPU 分钟。
若示例中所有设备均按 6 元/GPU 小时收费，这部分约 3 元；构建、冷下载、排队、存储和传输另列并计入总时间/费用。
真实执行使用各设备实时报价和历史耗时，不把这个算式当作实际发布报价。
任务按设备和缓存安排，不能为了等下一项任务长期空开 GPU。

### 4. 失败时按影响重测

如果 A 的一个 INT4 模型错误，发布保持未完成。先把错误下沉成小型可复现测试，再修代码。
重跑 A 的受影响算子和模型；B/C 的旧证据只有在执行依赖确实不变且适用于候选时才可保留。
重新构建的最终资产仍须完成 README 和安装验证；不能拿旧二进制的通过结果替代新资产。
若只是上传失败且资产字节没变，直接重试上传，不重新启动所有模型。

### 5. 放行和报告

全部必需行为有适用的通过证据、未满足项为 0，才允许晋升正式版。
报告同时列出范围、未测组合、各阶段时间、费用、重试和问题发现阶段。
例如演示结果为“32 GPU 分钟，按示例单价为 3.2 元”，这是运行阶段实测账单的表达方式，不是正确性指标。

## 实施顺序和完成定义

使用 Rust 复用现有 runner 和报告；每个任务完成检查后 PR 合并，再进入下一项。

1. **范围与选择器**：登记产品承诺、行为与路径；根据发布全部改动生成必测清单、选样理由和未覆盖项。验收：未知改动不被静默省略，代表缺失能被确定性测试检出。
2. **低成本数值与架构验证**：补真实参考差分和小合成架构，按变更涉及的后端验证。验收：有能检出错误的反例和真实后端证据；明确暂未覆盖的路径。
3. **发布证据校验与成本记录**：runner 输出逐行为状态和分阶段耗时；发布流程拒绝缺失、失败、不确定或不适用证据，并复用已验收资产。验收：故意缺证据或注入失败时不能晋升，完整证据才能晋升；上传重试不触发无谓重建。
4. **长尾轮转和调度改进**：根据历史成本安排剩余支持组合，登记最久未测项、发现阶段和 GPU 空闲费用。验收：轮转发现的适用失败进入发布必需清单，不能在下一轮被抹掉。

## 自动执行与发布入口

日常 PR 的 CPU CI 会从 Cargo 的实际测试产物中找到已登记的边界用例，
确认测试仍存在，再执行断言；删除测试、遗漏执行、断言失败、超时都会失败。
真实 GPU lane 在局域网 Mac 和 4050 上执行 RMSNorm、GEMM、SiLU Mul 的
对齐及尾部数值用例。编译通过、CPU 参考值或跳过不能替代 GPU 实际输出。
该范围不代表量化矩阵乘、Attention、KV 等算子已全部覆盖。

正式版使用 **Prepare formal release** 工作流输入版本号，自动生成协调版本
PR，通过必需 CI 后合并。版本合入主分支后，**Deliver formal release**
生成完整发布差异的计划，先阻断覆盖缺口，再构建候选包、执行选定模型回归、
核验全部证据并发布 Cargo、GitHub Release 和 Homebrew。最后实际安装公开
Cargo 包和 Metal/CUDA Homebrew 公式，执行启动验证，全部成功才算交付完成。

流程和失败恢复边界见[自动发版说明](release-delivery.md)。初次真实发布演练
仍需成功完成；不能把工作流文件、计划报告或局部测试通过当作正式发版已完成。
