## 产品目标

用户在同一台卡上换用更小的模型时，普通 `ferrum serve MODEL` 能利用多出来的容量。服务应说明采用的单请求上下文上限、可同时保留状态的请求数、单轮可执行的批宽和 token 预算。高并发的价值用成功完成请求的输出吞吐和用户可见延迟衡量。

客户端并发是施加的负载，服务端 `--max-num-seqs` 决定多少请求能同时保留状态，GPU 单轮参与数取决于执行批宽。主干 Auto 与候选 Auto 使用同样的客户端并发，各自选择服务端配置。为衡量自动选择的价值，还应在同一候选二进制、同一模型和请求轨迹上实测几个显式设置。对每种负载列出满足原延迟门限的最高实测吞吐，以及 Auto 与该配置的差距。若所有设置都失守，就分别给出吞吐与三项尾延迟，不把最快的超时配置称为最优。显存边界只能证明容量可行，实测覆盖的设置和负载决定了性能结论的范围。除了让客户端始终保持 C48，还按同一随机种子重放平均每秒 8、12、18 条的到达序列。各档比较达到全部 P99 门限的最高到达率，并列出首 token ≤ 2 秒、每输出 token ≤ 50 ms、完成 ≤ 5.15 秒的请求数和每秒按时完成数。这组按时条件用于每条固定 64 输出 token 的负载。

## 证据判读

- 每个候选都要通过长 prefill 和浅 decode 两种工作负载的预算复核。长 prefill 保留一份请求状态与完整上下文，单步 token 数取 `min(context, batch_tokens)`。浅 decode 按全部驻留请求计请求状态，每份只计 1 个已提交 KV token，步内工作区按实际 decode 批宽估算。候选会重新编译，因为宽度变化可能使算子或捕获图改用另一种布局。搜索只承诺找到已验证的可行宽度。
- 有启动图预热时，额外核算每个捕获宽度下各组序列的 KV 深度和该轮工作区。混合捕获模式在重放验证前会重新创建请求，估算也从新序列开始。CUDA 可以按四页一组增长 KV；预热估算和执行器共用页组取整与父请求上限，运行时回退到精确增长时实际用量可以更低。三项峰值分别和同一预算比较，预热结果在 `serving_concurrency_search.capture_warmup_peak_bytes` 中可见。纯按需图无需这一项。[编译计划核算](../crates/ferrum-execution/src/driver/composition.rs) · [预热执行与形状](../crates/ferrum-execution/src/driver.rs) · [物理页增长](../crates/ferrum-runtime/src/resource/sequence.rs)
- 可在 `GET /health` 读取 `auto_config.startup_memory_plan` 的请求限制、最终限制和两项峰值，用 `admission.active_sequences`、`maximum_active_sequences` 和 `queue_depth` 检查负载实际占用了多少席位。逐池核账读取 `cache.prefix_cache.dynamic_pools.pools[]` 的 `resident_bytes`、`free_bytes` 与 `pending_growth_bytes`。池已保留的空闲空间在下一波请求中可以复用。
- 启动时的可用显存是设备快照。短上下文的并发资格不构成多个请求都能同时达到最大上下文的保证。
- 分开记录同一执行形状的受管分配、原生分配器读数、外部整卡显存采样和进程 RSS。瞬时读数与采样高点带上单位、来源、覆盖范围以及缺测情况。估算失配需要定位到池或算子。
- 完成条件包括当前分支的行为回归、5090 的真实性能和容量边界证据，以及仓库约定的 workspace 和相关后端检查。显式调参臂用于判断还有多少利用空间。单项 SLO 失守、冷启动代价或硬件实测缺失均单列。

### 5090 首轮基线

v0.20.1 公开 SM120 包同时充当服务端和 Rust 客户端。权重是 Qwen3.5-0.8B Q4_K_M（Unsloth revision `6ab461498e2023f6e3c1baea90a8f0fe38ab64d0`），语义及 tokenizer 使用 Qwen revision `2fc06364715b967f1860aea9cf38778875588b17`。同卡已有服务常驻约 21.3 GiB。为共存显式设 6 GiB 预算，context 2048、每轮 token 上限 2048、关 thinking 和 prefix cache，基线由 Auto 决定并发。

```sh
ferrum serve "$GGUF" --semantic-source "$SEMANTICS" --tokenizer-source "$SEMANTICS" \
  --backend cuda --served-model-name ferrum --port 28441 \
  --runtime-memory-budget-bytes 6442450944 --max-model-len 2048 \
  --max-num-batched-tokens 2048 --disable-thinking --no-enable-prefix-caching

ferrum bench-serve --base-url http://127.0.0.1:28441 --model ferrum \
  --tokenizer "$SEMANTICS" --target-backend cuda --dataset random \
  --random-input-len 128 --random-output-len 64 --ignore-eos --temperature 0 \
  --sampling-seed 42 --seed 42 --enable-thinking false --concurrency-sweep 16,48 \
  --num-prompts 96 --warmup-requests 10 --n-repeats 3 \
  --latency-slo ttft:2000,tpot:50,itl:100
```

旧 Auto 选 32 个序列，普通与 SSE 算术请求均给出正确结果。576 个计时请求均成功并各产生 64 个 usage 输出 token。C16 三轮平均约 2278 output tok/s，均达到上述延迟目标。C48 平均约 2440 output tok/s，三轮均有延迟目标失守。计划报告 prefill 约 1.16 GB、浅 decode 约 1.58 GB。WSL 的 CUDA 可用内存快照与外部整卡读数有明显差异，本轮显式限定 6 GiB。

同版只增加 `--max-num-seqs 48` 后，另 576 个请求全部成功。C16 平均 2267 output tok/s，三轮均满足目标。C48 平均 2539 output tok/s，三轮可见 ITL P99 为 98.51、98.17、92.36 ms；旧默认分别为 100.74、105.62、108.52 ms。另一次不计入计时的 `/health` 观察到 48 条活跃序列。这组数据证明在该共卡负载下可以使用超过 32 的容量。独占 GPU 的测量将另列，避免混用机器状态。

| 原生默认，预算 29,186,378,183 字节 | 262144 | 256 / 32 | 1 | 4,571,966,672 / 6,299,774,768 / 1,872,949,040 |

- **同形状物理对账。** 6 GiB 下加 `--runtime-pool-preparation within-budget`，到就绪时读取静态字节 522,925,104、动态池实际驻留 5,517,106,320，合计 **6,040,031,424**，与选中浅 decode 的预备目标相符。这个零字节差验证该次受管预备；运行中 KV 继续增长，整卡显存还包含其他分配。
- **到达 256 的压力。** 普通按需服务和 `within-budget` 预备服务各测一次 C256，短输入、64 输出 token，每组 512 个请求全部成功。两种模式均实测同时驻留 256、活跃 decode 采样最大 32。按需服务队列最高 223，受管分配最高 6,438,026,416 字节；预备服务分别为 83 和 6,441,432,400 字节。两者均在 6,442,450,944 字节预算内。这两组只验证满驻留，现有次数不足以比较预备策略的延迟。
- 普通按需 C256 的这一轮达到 3074.7 输出 tok/s、48.04 请求/s；首 token P99 为 4820.7 ms，可见输出间隔 P99 为 48.1 ms。首 token 超过 2000 ms 目标，满载不满足交互延迟验收。该格使用 35–39 个实际输入 token，与正式 C48 负载长度不同。
- **紧预算可下调。** 32 条的捕获预热需 1,610,846,400 字节，比 1.5 GiB 多 233,664 字节。Auto 保留 2048 上下文与每轮 2048 token，选择 31。C31 压力实测 31 条同时驻留，62 个请求均完成 64 token。相同预算明确指定 48 时，服务在就绪前报告需要 1,927,949,440 字节并退出。
- **产品入口。** 无显式上下文、并发、批 token 或内存选项时，`serve` 保留模型声明的 262144 上下文、每轮 2048 token。无长上下文性能测量。`run` 的单次 CUDA 贪心算术请求返回 `5` 并正常退出，生效配置保留单请求并发。
- **长输入和前缀缓存。** 6 GiB 下开启标准前缀缓存选项，依次发送共享同一长系统消息的两个请求。两次服务端 usage 都是 1700 输入、2 输出 token，答案分别为 `5`、`6`，均正常结束。该模型与算子组合报告 `requested=true`、`enabled=false`，原因包含状态布局和 provider 资源覆盖，缓存条目与命中均为零。请求结束后活跃数回到零，两次受管分配均为 1,888,611,504 字节，其中动态池空闲 1,024,424,688 字节。这个结果区分了空闲 backing 驻留与前缀复用；有能力复用 KV 前缀的其他模型仍需单独测量。
